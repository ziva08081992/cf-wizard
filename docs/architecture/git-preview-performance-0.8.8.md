# Git preview: измерения 0.8.8

## Область и методика

Измерен полный `RustEngine.preview` (`engine_wall_ms`), включая compiler после формирования внутренних PlanMetrics. Открытие SQLite-индекса и последующая запись XML-комплекта измеряются отдельно и не входят в этот таймер. Это синтетический GitProvider без сети и платформы 1С. Результаты не являются SLA и не определяют эффект на реальных 344,220 секунды пользовательского журнала.

Вход: 64 справочника-заглушки, ссылки из одного общего модуля, полный вложенный inventory, невыдаваемые opaque payloads и непустые omitted modules. Готовый индекс и проверенные descriptor blobs сохраняются, source открывается заново с холодными деревьями. После cold preview и материализации тот же source используется для warm preview. Задержка каждого provider tree вызова — 20 либо 0 мс. Оба варианта читают полный состав; количество tree вызовов в основном cold-case осталось 266.

Для каждого значения задержки выполнено 27 соседних пар baseline/candidate, порядок AB/BA чередовался. По одному прогревочному запуску каждого бинарника сохранено отдельно и исключено из критериев заранее. Все измеренные samples и выбросы сохранены. P95 — описательный nearest-rank показатель на 27 значениях.

Критерии были зафиксированы до реализации: cold20 median не выше 50% baseline и минимум 22/27 улучшений; warm median для обеих задержек не хуже baseline более чем на max(2 мс, 10%). Cold0 — диагностический контроль без отдельного скоростного порога.

## Результаты

Все значения в миллисекундах; baseline — исходный последовательный путь, candidate — bounded inventory 0.8.8.

| Сценарий N64 | Медиана baseline | Медиана candidate | P95 baseline | P95 candidate | Улучшений из 27 |
|---|---:|---:|---:|---:|---:|
| Cold, 20 мс/tree | 5510,35 | 1629,55 | 5616,19 | 1786,55 | 27 |
| Warm, 20 мс/tree | 43,43 | 43,80 | 70,16 | 83,42 | 11 |
| Cold, 0 мс/tree, контроль | 88,88 | 116,99 | 120,33 | 177,20 | 1 |
| Warm, 0 мс/tree | 44,96 | 45,25 | 65,93 | 56,97 | 17 |

Основной cold-case ускорился в 3,38 раза, сэкономив 3,88 секунды (70,4%). Обе warm-медианы находятся в заданном допуске. При этом cold0 замедлился на 28,11 мс (31,6%): запуск потоков и синхронизация имеют систематическую цену на быстром холодном provider. Warm20 P95 также вырос; отсутствие хвостовых регрессий не заявляется. Статус cold0 — контроль, а не пройденный скоростной критерий.

Контроли размера при 20 мс/tree, по одной паре: N16 cold 1401,21 → 440,46 мс, warm 12,08 → 22,45 мс; N32 cold 2789,65 → 921,59 мс, warm 47,92 → 50,11 мс. Эти одиночные warm-значения не дают медианной оценки. Из-за отклонения N16 проведён отдельный проверочный ряд из 27 AB/BA пар на полностью прогретом N16 без provider обращений: median 12,00 → 11,60 мс, P95 15,42 → 12,45 мс, улучшились 19 пар. Первоначальный одиночный результат сохранён, новые samples его не заменяют.

## Корректность и ограничения

Во всех основных и дополнительных парах совпали сгенерированные входы, composition/reasons, полный наблюдаемый inventory, хеши выдаваемых файлов, XML настроек и readback roles. Opaque payloads не читались и не выдавались, обязательная заглушка не могла быть исключена. Candidate выполнял максимум четыре provider tree/file вызова одновременно; после success/error/cancel in-flight равен нулю. Same-path/OID, typed failure, cancellation/join и порядок ранней file error перед поздней tree error проверены адресно.

Окно содержит до четырёх owners. Все jobs завершаются до последовательных omitted-file reads и принятия результатов. Session/SQLite не передаются workers; обычная ошибка не отменяет пользовательский token. Готовый inventory используется без запуска потоков. LocalSource сохраняет последовательный путь. Семантика читателей, формат индекса и строгие проверки не менялись.

Реальные API Gitea/GitHub не вызывались. Расходы большого реального индекса, повторных чтений Git blob-кэша и полной пользовательской задачи требуют нового журнала с раздельными фазами. Отмена также зависит от прежних cooperative checks и timeout провайдера. Размер байтов inventory одного крупного объекта не ограничивается числом workers. Panic/poison/spawn-failure recovery рассмотрены статически; отдельное принудительное runtime-воспроизведение этих системных отказов не выполнялось.
