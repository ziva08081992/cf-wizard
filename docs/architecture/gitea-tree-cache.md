# Постоянный кэш деревьев Gitea

При открытии источника CF Wizard запрашивает текущую ревизию, дерево по SHA закреплённого коммита и описи, из которых формируется `GitInputs`. Размеры входов манифеста берутся из этих описей, включая дескрипторы, содержимое которых не понадобится в текущем предпросмотре. Дерево по SHA коммита служит начальной описью Gitea.

Деревья, которые нужны дальше, мастер ищет по OID в памяти процесса, на диске и у провайдера. Запись на диске имеет адрес `tree-cache-v1/<repo-hash>/<sha1|sha256>/<oid-prefix>/<tree-oid>` под заданным каталогом кэша. Хэш репозитория строится из провайдера, канонического адреса сервера и имени репозитория. Токен, ветка и путь выгрузки в запись не входят. Одинаковое неизменённое дерево пригодно для нескольких закреплённых ревизий.

## Проверка и восстановление

Запись содержит SHA-256 контрольную сумму и JSON с непосредственными детьми дерева. Лимит записи вместе с контрольной суммой составляет 16 МиБ. Мастер проверяет формат OID, имена, режимы и коллизии регистра, строит байты канонического Git tree и сверяет его хэш с ожидаемым OID из родительской описи. Ожидаемый OID определяет полноту описи. Отсутствие записи в кэше ведёт к запросу провайдера, а отсутствие имени в проверенном дереве может использоваться для доказательства отсутствия файла.

Ответ Gitea публикуется после получения полной описи и проверки OID. Временный файл создаётся рядом с итоговым. Атомарная замена открывает читателю целую запись. Повреждение, превышение размера, запрет reparse point или ошибка записи кэша оставляют доступным чтение у провайдера. Отмена проверяется до и после чтения и перед публикацией. Параллельный обход сохраняет четыре запроса на окно и общую загрузку для одного OID внутри окна.

Git tree удостоверяет имена, режимы и OID дочерних объектов. Размер вложенного blob, полученный с диска, допускается для ограниченной проверки локальных байтов по размеру и OID. Если валидных байтов в кэше нет, мастер один раз получает подтверждённую опись родителя до HTTP-запроса blob. Полученный размер задаёт предел чтения с проверкой преобразования в `usize` и прибавления единицы. Ошибка сети, отмена или расхождение подтверждённого размера с содержимым завершают текущую попытку без повторного запроса.

## Диагностика и откат

`provider.tree` учитывает все вызовы деревьев провайдера. Его дочерние показатели `provider.tree.bootstrap` и `provider.tree.size_refresh` отдельно показывают открытие и подтверждение размеров. Для диска доступны `cache.tree_disk_load`, `cache.tree_disk_write`, `cache.tree_disk_hit`, `cache.tree_disk_miss`, `cache.tree_disk_rejected` и `cache.tree_disk_write_error`. Эти показатели не содержат путей, адресов репозиториев или секретов. На прогретом диске дерево для обхода inventory доступно без запроса Gitea. При открытии нового процесса начальные описи по-прежнему подтверждаются провайдером.

Формат кэша отделён от блобов, исходников и индекса. Возврат к предыдущей версии не требует миграции. Новый мастер восстанавливает удалённые записи по запросу. Лимит 16 МиБ применяется к одной записи. Объём всего каталога увеличивается по мере появления новых OID.

## Результаты G1

Финальный стенд использовал выбранный `zlib-rs`, 64 сгенерированных объекта, готовый индекс и имитацию Gitea с задержкой 20 или 0 мс на запрос дерева. Для каждой задержки выполнены одна прогревочная пара и девять измеряемых AB/BA пар. В таблице медиана и p95 в миллисекундах. Новый процесс включает открытие источника, индекса и preview; прогретая память использует открытый источник. Подготовка фикстуры, сборка индекса и запись пакета измеряются отдельно.

| Задержка запроса | Состояние | Базовая версия, медиана / p95 | Новая версия, медиана / p95 |
| --- | --- | ---: | ---: |
| 20 мс | Пустой дисковый кэш | 1 947,534 / 2 034,801 | 2 029,849 / 2 130,434 |
| 20 мс | Прогретая память процесса | 45,303 / 49,733 | 45,196 / 47,066 |
| 20 мс | Новый процесс, прогретый диск | 1 871,331 / 1 948,392 | 469,532 / 480,856 |
| 0 мс | Пустой дисковый кэш | 327,067 / 407,495 | 506,803 / 569,297 |
| 0 мс | Прогретая память процесса | 46,138 / 49,873 | 43,646 / 47,988 |
| 0 мс | Новый процесс, прогретый диск | 277,915 / 289,215 | 385,168 / 401,715 |

При 20 мс новый процесс с прогретым диском ускорился на 74.91%. Inventory-запросы деревьев снизились с 264 до нуля при обеих задержках. В каждом новом процессе сохранены четыре начальных запроса. Соблюдены максимум четыре параллельных запроса и завершение без активных запросов.

Цена заполнения кэша при 20 мс: медиана +4.2%, p95 2 034,801→2 130,434 мс. При 0 мс медиана пустого кэша +55.0%, нового процесса с прогретым диском +38.6%. Повтор с прогретой памятью при 0 мс проходит порог. Все пороги зафиксированы до измерений. Предыдущий G1 на miniz также сохранён в `bench/tree/runs-g1-final`; таблица относится к финальному повтору.

Внешний стенд сверял отпечаток манифеста, наблюдаемые описи каталогов, проверки наличия и отсутствия, SHA-256 прочитанного содержимого, состав предпросмотра без метрик и SHA-256 файлов пакета и XML настроек после записи. Из контракта Readback сравнивались роли дескрипторов-заглушек и полных зависимостей. Внутренний тест дополнительно сравнивал весь `CompiledPackagePlan` и пакет до и после повторного открытия `GitSource` на том же дисковом кэше. [Тест GitSource](../../tools/cf-wizard-rust/crates/infrastructure/src/git_inventory_tests.rs#L649)

Исходные выборки и критерии сохранены в `bench/tree/runs-g1-zlib-final/summary.json` каталога аудита. Замеры относятся к синтетическому провайдеру и локальному диску стенда. Сокращение числа запросов должно помочь после перезапуска, если ожидание ответов Gitea занимает значительную долю RDP-предпросмотра. Реальный сервер Gitea, сценарий RDP и чтение пакета платформой 1С в этом прогоне не проверялись.
