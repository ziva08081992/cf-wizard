# Ядро зависимостей CF Wizard: выбор Datafrog

Статус: рабочая версия 0.8.5, один Datafrog-контекст на запрос. Сохранены 127 Rust-тестов и 57 точных kernel controls; выполнены восемь native CF/readback маршрутов. На каноническом источнике закрыты оба строгих selective merge регистра; старый sparse-пример сохранён отрицательным. [Дополнение к приёмке](../reports/cf-wizard-0.8.5-acceptance.md). Исчерпывающая coverage 3.1 остаётся открытой, change не архивирован. [Профиль](reader-profile-v1.md), [происхождение](provenance.md).

## Что выбрано

Для вычисления зависимостей выбран **Datafrog 2.0.1**, встроенная Rust-библиотека. Отдельный сервис не нужен. В продукте будет одно ядро; worklist остаётся контрольной реализацией сравнительного стенда.

Индекс уже хранит доступные факты об исходниках. Ядро решает другую задачу: какие объекты и части действительно понадобятся для текущего выбора пользователя, какие новые требования из этого следуют и почему они включены.

Модель различает:

- `object` — нужен объект, возможно в виде заглушки;
- `keep` — нужен конкретный фрагмент: поле, тип, файл, свойство или связь;
- `full` — нужен полный объект, включая все его исходные части.

**Выбранный алгоритм — инкрементальное вычисление положительного замыкания до неподвижной точки (semi-naïve evaluation).** Datafrog обрабатывает приращения фактов; правила добавляют требования, пока новых требований больше нет. Структурный координатор отдельно выбирает допустимый минимум там, где есть альтернативы, затем снова запускает замыкание. Например, присутствие документа не означает сохранение всех его движений: связь документа с конкретным регистром является отдельным фрагментом. Конечные непосредственные причины ведутся отдельно от ключей требований.

## Какие варианты сравнивались

| Вариант | Сильные стороны для этой модели | Ограничения, выявленные в сравнении |
|---|---|---|
| Собственная очередь новых требований — worklist | Простая специализированная реализация; хорошие горячие запросы и длинные цепочки | Fixed point, дедупликация и индексы соединений остаются собственным механизмом проекта; в измеренных первых запросах выше стоимость подготовки |
| Datafrog 2.0.1 | Готовые fixed point/dedup/join; хорошее соотношение подготовки, времени и памяти для текущего запроса Wizard | Правила платформы, readers, alternatives и объяснения всё равно принадлежат Wizard; не самый быстрый на каждой нагрузке |
| Ascent 0.8.1 | Краткая декларативная запись, особенно при добавлении сложного условия | Два проверенных адаптера дороги для последовательных структурных решений: постоянный контекст расходовал память, пересоздание индексов снижало память, но увеличивало время |

Это сравнение конкретных адаптеров и фиксированной модели, а не рейтинг всех возможных применений библиотек.

## Что измерено

Исследование от 14.11.2026: 27 наборов, 57 сценариев; у 53 есть дополнительный независимый медленный или аналитический oracle. Четыре широких реальных запроса проверены сравнением движков, замкнутостью и основаниями; это само по себе не доказывает отсутствие всех лишних включений. Отдельно выполнены 9 проверок одного и того же AND3-изменения.

Нормализованный реальный снимок: 28 294 записи объектов индекса, 191 887 ID фрагментов/внутренних требований, 680 318 строк положительных отношений и 3 417 структурных обязательств. ID включают внутренние маркеры и не равны количеству XML-файлов. Актуальность всего исходного индекса относительно любой будущей выгрузки не утверждается.

Основная серия — 390 отдельных процессов, один прогрев и 9 измерений на комбинацию, фиксированное перемешивание порядка; контроль второго адаптера Ascent — 36 запусков с тремя измерениями на комбинацию. Release, один поток, одинаковые нормализованные входы; digest каждого результата сверялся с проверенным ожиданием.

Пример — выборка 16 документов:

| Реализация | Медиана ядра, мс | Peak working set, MiB | Peak private commit, MiB |
|---|---:|---:|---:|
| Worklist | 6.81 | 24.76 | 22.62 |
| Datafrog 2.0.1 | 3.98 | 21.96 | 19.60 |
| Ascent: постоянный контекст R2 | 6 409.16 | 808.08 | 857.46 |
| Ascent: новые индексы с сохранением выведенных фактов R3 | 13 117.17 | 60.85 | 59.46 |

Время здесь — подготовка отношений, решение с альтернативами, объяснения/unresolved/digest. Чтение входного нормализованного JSON и запуск процесса измерялись отдельно; исходные XML/readers и сборка CF в эти значения не входят. Память — полный пик процесса, включая сериализацию; working set и private commit различаются.

Существенные контрпримеры сохранены:

- Горячая выборка тех же 16 документов: worklist **1.80 мс**, Datafrog **2.16 мс**.
- Серия 18 запросов с одной подготовкой: worklist **15.78 мс**, Datafrog **14.26 мс**.
- Длинная цепь с циклом: worklist **2.38 мс**, Datafrog **7.20 мс**.

В исследованном Wizard каждый preview открывал reader в новом задании, а solver оставался stateless между preview. Поэтому подготовка вместе с запросом важнее одной горячей операции. Сохранённый SQLite-индекс и подготовленные внутренние отношения solver — разные уровни повторного использования.

## Почему принято это решение

Datafrog даёт готовый вычислительный механизм при небольшой цене включения в текущую Rust-архитектуру. На измеренном профиле он сочетает хорошие первые запросы и умеренную память, не требуя сопровождать собственные fixed point/dedup/join.

Упрощение относится к владению механизмом. Добавление контрольного AND3 потребовало +20 строк у Datafrog и +19 у worklist; доказанного преимущества Datafrog по простоте каждой правки нет. Правила 1С, структурные альтернативы, полнота readers, provenance и XML-проекция остаются ответственностью проекта. Независимый разбор Astra подтвердил выбор по проверенному стенду; независимый аудит продуктовой интеграции является отдельным этапом.

Разница первых запросов составляет несколько миллисекунд. Заметное ускорение полного пользовательского сценария не обещается: source I/O, материализация и платформа 1С измеряются отдельно после интеграции.

## Что требуется от интеграции

1. Сохранить проверяемый существующий индекс и адресно дополнить факты поддержанными readers; не переиндексировать всю конфигурацию для каждой selection.
2. Использовать один kernel для preview и повторного расчёта при exclusions. Datafrog context с `Rc<RefCell>` живёт внутри фонового задания; между потоками передаётся owned план.
3. Сохранить optional/required policy и конкретные fragments. Для registrar choice предпочитать подходящий уже включённый документ, обязательно добавляя точную link; этот продуктовый comparator имеет отдельный oracle сверх source-first benchmark.
4. При отсутствующей подтверждённой обязательной зависимости показывать состав и ошибки, запретить сборку в UI и application. Не превращать обычный/неизвестный динамический текст в обязательный endpoint автоматически.
5. Сохранить source proofs, точные полные XML/BSL, role-aware stub projection, resource contents и полный native/readback pipeline.
6. После реализации выполнить product/regression/native проверки и независимый аудит **Astra / max**, затем собрать окончательный EXE и обновить manifest и документы поставки.

Полнота читателей BSL, форм, СКД, XDTO и остальных свойств этим kernel benchmark не доказана. Восемь семейств положительных правил и ограниченный источник фактов не означают полный анализ произвольной конфигурации 1С.

## Когда пересмотреть выбор

Если преобладают длинные цепочки, существенно меняется частота повторных запросов или модель усложняется новыми отношениями, повторить сравнение на том же контракте и новых реальных профилях. Worklist остаётся обоснованной альтернативой; выбор Datafrog не является безусловным доказательством превосходства.
