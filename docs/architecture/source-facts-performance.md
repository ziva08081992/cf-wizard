# Обработка SourceFacts V2

Rust-мастер читает существующий индекс со строками `cf-source-facts-v2`. Строка хранит типизированный JSON в zlib, распакованный payload ограничен 64 МиБ на объект. Версии схемы, readers и подписи facets сохраняются. Предпросмотр читает индекс без перезаписи.

Валидация сверяет SHA с наблюдениями источника по ссылкам на строки. Она проверяет существование родителей, ссылки и coverage notes по прежним правилам. Если адрес каждого родителя строго короче адреса потомка, цикл невозможен и дополнительная структура не нужна. Для остальных допустимых адресов обход хранит ссылки на посещённые адреса и начало каждого обхода. Повтор внутри текущего обхода означает цикл, а посещённый ранее адрес завершает проверку цепочки.

После получения XML адреса узлов строятся в порядке токенизации, где родитель предшествует потомку. Адрес потомка дополняет адрес родителя URI, локальным именем и ordinal узла. Документ сверяет path, SHA, byte span, tag и parent с XML и записывает proof текущего снимка. Новые факты передаются в документ по владению. Факты, которыми делится предыдущий recipe, копируются для обновления proof. Записи без запрошенного документа сохраняются в `DemandCache` для повторной подготовки.

Повреждённая или несовместимая строка закреплённого индекса возвращает ошибку. Отсутствующая строка обрабатывается прежним путём. Локальный индекс сопоставляется с хэшем фактически прочитанного XML. Отсутствие строки, несовпадение хэша или ошибка декодирования допускают извлечение из этого XML. Несовпадение span, tag или parent в кэшированном документе остаётся ошибкой. Данные распакованных объектов принадлежат текущему сеансу и его recipe, общего кэша между независимыми предпросмотрами нет.

## Проверка на множестве объектов

`tools/cf-wizard-rust/tests/facts_performance.py` управляет отдельным offline-тестом. Команда `prepare-control` копирует baseline в отдельный каталог и добавляет к копии тот же замер адресов, что и у кандидата. Из release-сборки контрольного теста команда `freeze` получает исторические V2 fixtures и сохраняет SHA-256 XML и payload. Все 822 объекта синтетические. Размеры равномерно увеличиваются степенью двойки до суммарного объёма V2 JSON от 1 ГиБ. Два исполняемых тестовых файла затем читают те же fixtures.

Команда `compare` выполняет семь соседних пар в чередующемся порядке после одной отдельной пары прогрева. Каждый процесс создаёт новый сеанс с 822 кэшированными документами, 78 структурными проекциями и четырьмя повторными декодированиями. Отчёт содержит интервал сеанса, отдельный замер encode, измерения вложенных этапов, пиковый рабочий набор и контрольный хэш фактов, адресов, структурных проекций и proof. Времена вложенных этапов пересекаются. Проверка SQLite, реальные Git-запросы, GUI и полный пользовательский предпросмотр измеряются отдельно.

В локальном A/B с `miniz_oxide` первый проход по 1,82 ГиБ распакованного V2 занял 6,245 с вместо 9,272 с по медиане, p95 составил 6,436 с вместо 9,410 с. Максимальный пиковый рабочий набор вырос с 4 178,2 до 4 249,0 МиБ и уложился в предел протокола. Контрольный хэш результата совпал у всех 16 процессов. Медиана построения адресов снизилась с 1,737 до 0,292 с, валидации при декодировании с 1,024 до 0,204 с. Эти результаты относятся к синтетическому стенду.

## Реализация сжатия

Для `flate2` включён feature `zlib-rs`. Обе тестовые сборки для выбора backend получены из одного снимка исходников с зафиксированными зависимостями. Feature активирует уже закреплённый `zlib-rs 0.6.8`. Граф пакетов и версий в `Cargo.lock` сохранён, SHA-256 файла совпадает с контрольным. Кодек сохраняет типизированный JSON V2 и контейнер zlib.

В отдельном A/B на тех же 822 объектах переход с `miniz_oxide` на `zlib-rs` сократил медиану первого прохода с 5,855 до 5,537 с (−5,44% при пороге 5%), p95 с 5,884 до 5,780 с. Максимальный пиковый рабочий набор составил 4 247,9 и 4 249,0 МиБ соответственно. Во всех 16 процессах совпал семантический хэш. Обе сборки прошли по 25 проверок V2, ZIP, GZip, содержимого пакетов и readback.

Первый A/B измерял изменения обработки на одном backend. Второй измерял выбор backend на одном снимке кода. У каждого сравнения своя контрольная сборка и свой процент ускорения. Сквозную регрессию полного предпросмотра проверяет отдельный прогон D4.
