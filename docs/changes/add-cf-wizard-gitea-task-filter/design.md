## Context

Фабрика источника открывает каталог метаданных по Configuration.xml. В режиме Git каталог содержит клиент, каталог выгрузки, ветку и SHA. GiteaClient использует HTTPS, PAT чтения в заголовке и отключает редиректы. Qt-мост уже выполняет сетевые операции в рабочем потоке, фильтрует дерево по имени и отметкам и сбрасывает предпросмотр при изменении выбора. Это описание исходного Python/Qt-пилота. Текущий UC-01 выполняется Rust GitSource и интерфейсом Wry/WebView2; новые правила поиска описаны в решении 6. Legacy Python не изменяется. Платформенные вызовы 1С и правила BSL к нему не относятся.

## Goals / Non-Goals

Использовать контракт открытого снимка и существующую модель отметок. Для поиска достаточно метаданных коммитов и путей. Кэш содержимого, индекс SQLite зависимостей и механизм сборки остаются частью существующего сценария.

## Decisions

1. **Читать историю по SHA.** Использовать GET commits со страницами, датой начала для ограниченного периода и отключёнными files, stat и verification. Проверять продвижение по SHA и завершать по пустой странице. Размер возвращаемой страницы может ограничить сервер. Счётчик общей истории может включать коммиты вне периода. Документированный REST не предоставляет поиск по сообщению. Веб-страница поиска имеет собственную схему входа и разметку. Выбор REST сохраняет действующий транспорт и права. [История Gitea 1.25](https://docs.gitea.com/api/1.25/operations/repo-get-all-commits/) · [Маршруты Gitea 1.25.3](https://github.com/go-gitea/gitea/blob/v1.25.3/routers/api/v1/api.go#L1314-L1335)
2. **Читать пути только по совпавшим SHA.** В текущем Rust-маршруте применять решение 6: полный ключ с границами токена либо буквальный свободный фрагмент. Для каждого уникального совпавшего SHA получать files через GET git/commits/{sha}. Проверять форму ответа, отбрасывать пути вне каталога выгрузки и считать уникальные пути. Отдельный запрос по совпадениям снижает серверную работу по сравнению с вычислением путей для каждой строки истории. [Данные коммита Gitea 1.25](https://docs.gitea.com/api/1.25/operations/repo-get-single-commit/)
3. **Использовать существующее сопоставление владельца.** Переиспользовать DesignerExport.describe и правила _owner_descriptor из adapters.py. Описание владельца сопоставляется по открытому Configuration.xml. Удаление вложенного файла не мешает сопоставить путь с живым объектом. Пути без владельца в дереве учитываются отдельно. Материализация каждого изменённого файла и обход каталогов Git для сопоставления не нужны.
4. **Хранить результат рядом с состоянием каталога.** Qt-мост передаёт в поиск активные ветку, SHA, ключ и период. Worker проверяет отмену между HTTP-запросами. Успех публикует набор ключей и счётчики только для того же снимка. Дерево пересекает Git-отбор с текстовым поиском и «Только выбранные». Смена снимка очищает отбор, а обновление SQLite той же ревизии сохраняет его. Команда «Отметить найденные» добавляет ключи к текущему выбору и один раз сбрасывает предпросмотр, если набор изменился.

5. **Передавать своё число дней через существующий запрос.** `GitTaskQuery.create` получает необязательный `days=90`, проверяет положительное целое, переполнение даты и поддерживаемый диапазон 1970–2099 ([параметры GitHub](https://docs.github.com/en/rest/commits/commits#list-commits)); отказ оформляется понятным `ValueError` с предложением выбрать всю историю. Режим всей истории оставляет обе даты пустыми. Qt-мост проверяет ввод до запуска worker. HTML расширяет общее тёмное меню вариантом «Указать дни…» и показывает числовое поле только для него; занятость блокирует поле вместе с остальным поиском. Gitea и GitHub уже передают `since/until`, поэтому их транспорт и права не меняются. Границы вычисляются один раз в UTC при запуске поиска. Значение поля живёт в текущем окне; новый формат настроек не нужен.

6. **Расширить поиск текущей Rust-версии без нового API или доменного слоя.** Нормализацию и построение matcher оставить в существующем маршруте `GitSource::search`. Сначала проверять исходную строку на `char::is_control`, затем обрезать внешние пробелы и проверить непустое значение/предел 256 байт UTF-8. Model не должен заранее терять управляющие символы через trim. Ключ `[A-Za-z][A-Za-z0-9_]*-[0-9]+` распознаётся только для выбора режима: сохранить нынешние границы `[^\pL\pN_]`, включая отказы для ERP-1234, XERP-123 и ERP-123_test. Остальной текст искать как экранированную регистронезависимую подстроку без внешних границ. Gitea/GitHub получают только существующие параметры истории; поисковый текст фильтруется локально. Поле назвать «Комментарий коммита Git», номер задачи оставить примером. В JS использовать UTF-8-счётчик для того же предела вместо несогласованного ограничения 64 UTF-16 единиц. Не применять правила имён файлов, веток или командной строки. Сквозные тесты должны вызывать настоящий GitSource::search с непустой историей, а не проверять только helper.

## Risks / Trade-offs

- История может быть длинной. По умолчанию ограничить период, показать счётчик обработанных коммитов, выполнять запросы в фоне и поддержать отмену. Обрыв, повтор страницы или достижение предела страниц оформлять как незавершённый поиск.
- Gitea определяет список путей для merge и переименований. В пилоте проверить, что выдача на характерных коммитах совпадает с веб-историей. Подбор объектов использует их состояние в открытом снимке и может захватывать более поздние правки этих объектов.
- Ошибки API показывать существующим безопасным форматом. В журнал поиска не передавать токен, заголовки и тексты коммитов.

## Migration Plan

Функция использует текущую конфигурацию подключения. Нового формата настроек или миграции SQLite для этого сценария нет.
