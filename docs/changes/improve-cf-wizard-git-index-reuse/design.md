## Context

GitFiles хранит снимки в repo/branch/SHA/config и постоянные blobs. DependencyIndex выбирает стабильное имя SQLite по источнику и ветке, но IndexReader проверяет абсолютный SHA-путь metadata.source. Обновление уже пропускает повторное скачивание и парсинг неизменных XML, однако читает и хеширует их все. Цель описана в proposal.md; Full Discovery выполнен read-only.

Точки исполнения: открытие ветки через фабрику → GitFiles → публикация каталога → _sync_index; кнопка обновления → DependencyIndex.refresh/update_git_index; предпросмотр/сборка → DesignerPackageBuilder → helper_worker → IndexReader. BSL, метаданные, API 1С и информационные базы не меняются, поэтому проверки платформы 8.3.27 и v8std здесь неприменимы.

## Goals / Non-Goals

Цель дизайна — заменить привязку пригодности к физическому SHA-каталогу доказательством одинаковых входов, сохранив текущее закрепление файлов сборки за SHA. Новый actor-goal не вводится; подготовка Git-источника остаётся существующим сценарием. Локальный режим, авторизация и partial_cf.py сохраняют свои контракты.

## Decisions

1. **Неизменяемые входы.** Нейтральная модель GitIndexInputs содержит стабильный ключ источника, SHA происхождения и упорядоченные записи path/OID/size/owner/roles. Роли configuration/descriptor/registrar могут совмещаться. Данные отделены от Qt, транспорта и SQL; GitFiles строит модель из проверенных полных деревьев и текущего Configuration, а не наличия файлов на диске. Файл Configuration, все его descriptors, включая Language, и все непосредственные Documents/*.xml входят обязательно. Пропуск неизвестного Documents оставил бы устаревших регистраторов.
2. **Полный манифест в SQLite.** Дополнительная таблица git_inputs хранит записи, метаданные — source_key, fingerprint, indexed_revision, версию манифеста и совместимость фактов/helper. Fingerprint считается детерминированно по отсортированным нормализованным записям. Версия представления манифеста отделена от версии смысла фактов. Один fingerprint без строк исправил бы только готовность и сохранил полный XML IO при обновлении, поэтому выбран per-file OID.
3. **Проверка чтением.** Фоновое открытие источника получает входы и проверяет SQLite. Совпадение источника, helper, версий и fingerprint означает готовность для текущего каталога без retag записи metadata.source. Исходная SHA остаётся происхождением. _sync_index не делает HTTP; результат входов кешируется на неизменяемом GitFiles. Периодический опрос HEAD продолжает только сообщать об изменении ветки, а не запускает индексацию.
4. **Обновление по кнопке.** Разность строк старого и текущего манифеста определяет добавления, изменения, смены владельцев/ролей и удаления. Для изменённых bytes используется существующий ensure с Git hash-проверкой. Неизменные XML не читаются и не хешируются; прямые факты переиспользуются. DefinedType раскрывается при потреблении, поэтому неизменные XML потребителей перепарсивать не требуется. Документ может обновлять и собственные факты, и RegisterRecords. DDL, факты, связи и манифест публикуются одним приватным draft с действующей защитой от конкурентной замены.
5. **Предпросмотр без всех файлов.** Git-ветви descriptor_inventory в preview/prepare и проверке сборочного снимка заменяются проверенным манифестом и текущей SHA. _verify_plan, lazy ensure и проверка реально прочитанных bytes сохраняются. Индекс открывается с ожидаемым source_key/fingerprint/helper во всех местах, включая helper_worker, в согласованном SQLite read snapshot. Полный манифест не требуется копировать в каждый job, если достаточно проверенного контекста и таблицы в SQLite. BSL-only новая SHA сохраняет индекс, но инвалидирует прежний Preview и читает новый модуль. Локальный filesystem inventory остаётся прежним.
6. **Совместимость.** Локальный v1 работает по прежним правилам. Старый Git v1 допускается только по прежнему точному source/SHA/helper-контракту; перенос на другую SHA без манифеста не подтверждается. Явное обновление создаёт частную копию и один раз сверяет все входы, связывая их OID с фактами. При совпадении helper и проверенного содержимого факты можно сохранить; при недоказанной идентичности или изменении helper они извлекаются заново. Автоматического изменения SQLite при подключении нет.
7. **Журналы.** Проверка и обновление фиксируют провайдера, ветку, SHA, безопасный итог, количество входов/изменений/удалений/переиспользований и время. Сеть, чтение XML и извлечение фактов учитываются отдельно, чтобы не называть уже существующую инкрементальную сеть новым ускорением. Токены и заголовки не журналируются.

## Risks / Trade-offs

- Пропущенный XML или роль даст ложную готовность → полный проверенный tree, Configuration и отдельное полное Documents, тесты добавления/удаления/owner mapping.
- Смена только BSL при прежних XML → повторное использование SQL не означает повторное использование Preview; проверяется текущая SHA и содержимое реально используемых файлов.
- Старый helper, повреждённый blob или чужая база → отказ совместимости и явное обновление, без ослабления глобальной проверки source локального режима.
- Одновременное обновление другим окном → согласованный read snapshot и проверка ожидаемого прежнего файла перед replace; ошибка сохраняет старую SQLite.
- Configuration изменён косметически → консервативно требовать кнопку. Это допустимый лишний запрос обновления, а не риск пропуска зависимости.
- Проверка требует O(N) записей и запросов каталогов, копирование draft имеет стоимость размера SQLite → замерить холодный, повторный, BSL-only и один изменённый XML; время и размер пока не измерены.

## Migration Plan

После утверждения этого плана уточнить противоречащие R4/R5 старого Gitea change, сохранив запрет смешивать реальные файлы разных SHA и совместимость GitHub R2. Добавить формат манифеста и чтение legacy без незаявленной записи. Проверить миграцию по кнопке, ошибку и откат, затем snapshot guards и UI. Не удалять старые базы/кэш. Обратный переход на старый EXE может не принять новый Git-манифест; локальный v1 должен оставаться совместимым. Выполнить отдельное смысловое ревью Full Path до приёмки.
