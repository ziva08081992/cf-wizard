## Goals / Non-Goals

**Goals:** реализовать UC-01 через сменяемые Git API, сохранить старое подключение Gitea, целостность файлов и точный отбор задачи; ограничить число запросов начальной индексации.

**Non-Goals:** перечислены в proposal. Дополнительно не менять SQLite-схему, алгоритм замыкания зависимостей, стратегию сборки CF, механизм обновления локальной XML-выгрузки и не добавлять общую отмену создания индекса в эту доработку.

## Decisions

### D1 Общий контракт и две самостоятельные стратегии

Фабрика клиента выбирает `gitea`/`github` по явному сохранённому provider. `GiteaClient` и новый `GitHubClient` реализуют одинаковые операции: ветки, SHA ветки, история, пути коммита, дерево, один blob и пакет XML. Общие типы, проверка HTTPS, ошибок и файлов/кэша отделяются от API-конкретных endpoints; старые импорты Gitea при необходимости сохраняются совместимыми re-export.

GitHub не наследуется от Gitea с подменой URL: форматы деревьев, авторизация и batch API различаются. Qt выбирает фабрику, а не конкретный клиент. `GitFiles`, каталог, SQLite, предпросмотр и сборка остаются потребителями общего контракта. Это реализует UC-01, R1/R2/R4/R5.

Альтернативы: условные ветки GitHub во всём UI усложняют интеграцию; копирование всего кэша/индекса в новую стратегию создаёт две расходящиеся реализации.

### D2 Область адресов, секреты и настройки

Для GitHub поддерживается GitHub.com: `https://github.com` и `https://api.github.com` приводятся к одному каноническому адресу. HTTP API направляется только на `https://api.github.com`; Enterprise пока явно отклоняется. Gitea продолжает принимать проверенный пользовательский HTTPS base URL.

При отсутствии provider читается Gitea. Для старой Gitea сохраняется прежняя формула Windows credential target и cache/index identity. Для GitHub вводится отдельный provider namespace; ключи включают канонический host, repository, directory, branch и закреплённый SHA там, где это нужно существующему кэшу. Произвольные значения provider отклоняются до чтения секрета/HTTP.

Выбор другого API очищает введённый secret, remember и список веток; поле сервера получает очевидное значение нового сервиса. Токен из WinCred читается только для выбранных provider/host. «Удалить токен» получает текущие значения окна, а не прежние сохранённые настройки; другой target не удаляется. Сохранение PAT происходит только после успешной проверки и явного remember. PAT не передаётся HTML/JS, не сериализуется, не попадает в исключения/журнал.

Общий HTTP-слой сохраняет проверку TLS, запрет redirects и timeout. Не переходить по `download_url`, `Link` или `url` из ответа с Authorization: endpoints и номера страниц формируются самим клиентом. Для GitHub используются Bearer PAT и закреплённая документированная REST API version. Ошибки показывают безопасный статус/причину; тело и Authorization не логируются. Retry-After/reset принимаются только как проверенные числовые данные. R3/R6.

### D3 Закреплённые деревья и двоичные файлы GitHub

Последовательность: exact branch ref → commit SHA → `GET git/commits/{sha}` → root tree SHA → нерекурсивные `git/trees/{treeSHA}` → выбранный каталог. Параметр `recursive` отсутствует: даже `recursive=false` включает рекурсию по контракту API. Любой `truncated=true` либо неверный SHA/entry считается ошибкой полноты.

Обычные файлы читаются по известному blob SHA через GitHub blob API; ни ветка, ни URL скачивания из ответа не заменяют закреплённую идентичность. До принятия проверяются размер и Git blob hash; сохраняются ограничения Windows-путей, запрет symlink/submodule/LFS и проверка коллизий. Большой неподдерживаемый blob завершается явной ошибкой, а не усечённым успехом. R4.

### D4 Пакет XML через read-only GraphQL

Существующий `GitFiles.metadata` уже собирает до20 XML на пачку. GitHub реализует эту операцию query с aliases `Repository.object(oid:...)`; owner/name/OID передаются variables. Кэшированные XML не скачиваются повторно. Начальная пачка не больше20 объектов; клиент дополнительно разделяет пачки по ожидаемому суммарному размеру из проверенного дерева. Предельные размеры запроса/ответа ограничены. В запросах отсутствуют mutation.

Для каждого blob проверяются typename, OID, byteSize, isBinary, isTruncated и UTF-8 bytes восстановленного text; принимаются только точные размер/hash. Binary/null/усечение либо несовпадение восстановленных bytes направляют конкретный blob в ограниченный REST fallback с проверкой. GraphQL top-level errors, отсутствующий alias и потеря доступа не маскируются неполным успешным пакетом. Ошибка не заменяет существующий индекс; автоматического расширения PAT нет. При timeout/resource errors допустимо ограниченно делить текущую пачку; auth/rate limit не вызывают бесконечных retry.

Причина: отдельный REST-запрос для каждого из примерно29тыс.XML превышает обычный PAT-бюджет5000/час. Пачки20 дают около1450 HTTP-пакетов плюс дерево/fallback — это оценка количества запросов, не замер скорости и не равенство GraphQL points. Бюджет наблюдается через rateLimit; реальное время измеряется на пилоте. Альтернатива ZIP/clone нарушает согласованный выборочный доступ. R4.

### D5 Полные пути коммита через сравнение деревьев

История GitHub читается с закреплённого SHA, с пагинацией и текущим точным matcher ключа задачи. Для совпадения пути определяются сравнением tree SHA коммита и первого родителя с пропуском одинаковых поддеревьев. По возможности обход ограничен выбранным каталогом выгрузки. Для initial commit исходное дерево пустое; merge сравнивается с первым родителем; rename представлен удалённым старым и добавленным новым путём. Gitea остаётся на своём API, одинаковая merge-семантика двух сервисов без отдельной проверки не утверждается.

Причина: обычный GitHub get-commit files возвращает максимум3000 файлов, поэтому REST-pagination/diff/patch не обеспечивают полноту. Внутренний обход проверяет cancellation Event между HTTP-запросами и перед публикацией. Общий контракт путей получает cancellation; расширение Gitea сохраняет её текущий результат. Предыдущие отметки/фильтр/предпросмотр не меняются при ошибке или отмене. R5.

### D6 Проверки и доставка

Адресные unit/integration с синтетическим HTTP покрывают provider routing, legacy-настройки/credential/cache, отсутствие redirects/утечки, полные ветки и историю, GraphQL/REST-byte parity, большие коммиты/переименования/merge, отмену и атомарность индекса. Qt smoke использует изолированный профиль и проходит настоящий UI-поток подключения/открытия. Отдельно проверяется сохранение рабочего локального сценария.

После последней правки обязательны два независимых этапа: ревью эффективности и обоснованности решения с двумя разделами; затем смысловое ревью сценария Full Path. Отчёты фиксируются в execution. BSL-диагностики и платформенная сборка конфигурации не применяются к этому Python/API diff; их не обозначать пройденными. В PR указываются выполненные проверки и отдельно непроверенный private GitHub pilot. EXE в этом запросе не пересобирается. R6.

## Risks / Trade-offs

- Различия GraphQL text и исходных BOM/CRLF → проверка bytes/hash, REST fallback только конкретных blobs.
- Внешние rate/SSO/organization ограничения → безопасная ошибка, сохранение предыдущего состояния, проверка минимального PAT на пилоте.
- Крупный Merkle diff делает много запросов → SHA-кэш и пропуск равных поддеревьев, отмена между запросами; полнота важнее скрытого усечения.
- Рефакторинг общего Git-кода может повредить Gitea → старые targets/пути и регрессионные тесты обязательны, изменение Gitea API-протокола не требуется.
- Private Blob с fine-grained Contents:read и реальное время ещё не проверены → узкий пилот отдельной задачей; права автоматически не повышать. Поддержка fine-grained PAT в GraphQL документирована, но это не функциональная приёмка нашего клиента.

## Migration Plan

1. Проверить актуальный чистый main после PR #1; создать `codex/github-source` либо свободное имя с этим префиксом.
2. Реализовать обратно совместимые настройки и стратегии; не переписывать чужие/несвязанные правки и не читать пользовательские токены для тестов.
3. Пройти адресные проверки и ревью; открыть PR только по diff этой доработки, проверить base/head, выполнить разрешённое слияние без обхода обязательных checks.
4. Rollback — revert PR. Legacy Gitea namespace и старые настройки не удаляются, GitHub-кэш и токен остаются самостоятельными; отзыв секрета выполняет пользователь.

## Open Questions

- На реальном private-репозитории предстоит проверить fine-grained PAT только для выбранного репозитория с Contents:read, включая правила организации. Это acceptance окружающей среды, а не разрешение запросить более широкие права.
- Нужно измерить cold/warm/incremental индексацию и запросы на размере рабочей конфигурации. До измерения обещание ускорения отсутствует.
