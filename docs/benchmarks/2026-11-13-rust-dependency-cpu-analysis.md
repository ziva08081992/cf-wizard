# Расчёт зависимостей Rust: профиль и два прототипа, 13.11.2026

По запросу «Посмотри пожалуйста, а сможешь оптимизировать расчет зависимости?» проведён анализ и эксперименты на отдельных диагностических копиях. Основные исходники приложения и GUI EXE не изменены. Рекомендуемый кандидат — повторное использование готовой заглушки при неизменности её точных входов в рамках одного предпросмотра.

## Подтверждённый профиль

Диагностический профиль содержит вложенные таймеры с inclusive/exclusive временем и счётчиками вызовов. Это инструментированные запуски, их время не подменяет A/B-замеры обычных бинарников.

Для прежнего регистра `AccumulationRegister.АмортизацияОС` (84 заглушки), SQLite:

- `Xml::parse`: 167 вызовов, суммарно 28,1 МБ входного XML, около 0,176 с.
- `clean_properties`: около 0,010 с вместе с вложенным `scan`.
- `Session::facts`: около 0,00034 с; `index_members` при попадании в SQLite не вызывается.

Для прежнего смешанного набора (92 заглушки): `Xml::parse` — 210 вызовов, 28,7 МБ, около 0,193 с. Основной подтверждённый вычислительный резерв — повторный разбор и построение заглушек; deep-copy Facts на этих четырёх выборах не является главным расходом.

Повторные проходы нельзя просто удалять. Состав `present` растёт в ходе замыкания и способен изменить ранее сформированную заглушку. `scan_file/having` также зависит от текущего included-набора. Эти действия сохранены.

## Эксперимент 1: полный кэш разобранного XML

XML разбирается лениво в прежней точке первого build; дерево сохраняется до конца Session. Сборка результата при dirty/present всё равно повторяется.

Медианы трёх измерений полного предпросмотра, SQLite:

| Набор | Прежний Rust | Полный XML-кэш | Пик WS прежде → после |
|---|---:|---:|---:|
| Регистр | 0,954 с | 0,905 с | 113,1 → 241,8 MiB |
| Смешанный | 1,118 с | 0,994 с | 115,5 → 244,0 MiB |

Все результаты 64 запусков совпали, но выигрыш 5–12% сопровождается более чем двукратным пиком памяти. Такой неограниченный кэш первым решением для внедрения не рекомендуется.

## Эксперимент 2: лёгкое повторное использование результата

Вместо XML-деревьев используется уже существующий `Built.output`. Дополнительно в Session сохраняются полный `StubSpec` и ответы всех фактически выполненных проверок `present.contains`. Повторный builder пропускается только при точном совпадении спецификации и этих ответов.

Если `.all()` остановился на первом false, ненаблюдённые ключи не влияли на результат. Изменение наблюдённого false→true инвалидирует запись и при повторном построении расширяет трассу. Кэш не переходит в Recipe, следующую Session или другой запуск.

На попадании пропускается только создание output: выбор файлов, сканирование готового XML, `note`, `scan_file/having`, причины и dirty-обработка продолжаются. Проверки исходников и `Recipe::verify` сохраняются. Публичные сигнатуры-wrapper для BTreeSet не меняются.

Дополнительно проверены два чистых упрощения: не вычислять `foreign` для protected-свойства, которое всё равно сохраняется; заменить линейный поиск позиции члена картой с сохранением правила «первая позиция, последнее значение», включая вложенные columns.

Медианы трёх измерений полного предпросмотра:

| Набор | Режим | Прежний Rust | Лёгкий кэш | Сокращение времени | Пик WS прежде → после |
|---|---|---:|---:|---:|---:|
| Регистр | XML | 0,962 с | 0,846 с | 12,1% | 111,9 → 109,9 MiB |
| Регистр | SQLite | 0,953 с | 0,845 с | 11,4% | 114,1 → 112,8 MiB |
| Смешанный | XML | 1,027 с | 0,933 с | 9,2% | 113,0 → 111,8 MiB |
| Смешанный | SQLite | 1,085 с | 0,963 с | 11,2% | 115,5 → 114,1 MiB |

Для регистра скорректированная граница собственно расчёта с SQLite: 0,853→0,745 с; для смешанного набора: 0,952→0,846 с. Из Rust вычтены две snapshot-проверки, которые Python выполняет снаружи resolver; оставшееся время всё ещё включает IO/guards/SQL, а не только CPU.

Диапазоны трёх нынешних измерений, SQLite: регистр baseline 0,936–0,955 с / кандидат 0,832–0,876 с; смешанный baseline 1,043–1,110 с / кандидат 0,947–0,968 с. Измерения двух экспериментов проходили последовательно; сравнивать следует парные baseline/candidate внутри одного эксперимента.

На справочнике существенный выигрыш не подтверждён: 0,301→0,293 с с SQLite, в пределах небольших колебаний. На модуле 0 заглушек; показанное 0,172→0,122 с нельзя приписывать memo — новый путь там не используется, наблюдались выбросы времени snapshot. Для малых наборов ускорение не заявляется.

## Методика и проверки

Прежние четыре выбора: `CommonModule.ZipАрхивы`, `Catalog.Валюты`, `AccumulationRegister.АмортизацияОС`, их объединение. Прежняя XML-выгрузка ERPUH и та же SQLite. Для каждого режима XML/SQLite — один прогрев и три парных измерения в чередующемся порядке, отдельный процесс на запуск. Каждый эксперимент — 64 запуска, вместе 128; отдельно выполнены 8 инструментированных запусков профиля.

A/B-бинарники не содержат профилирующих таймеров. Пиковый рабочий набор Windows получен через GetProcessMemoryInfo при наблюдении дочернего процесса. Это peak working set процесса, не точное число байт кэша и не private commit. Одинаковая процедура наблюдения применена к обеим версиям. OS-кэш не очищался; отдельные фоновые колебания видны в raw-данных.

Во всех A/B-запусках совпали normalized composition, причины/обязательность, члены/предупреждения, source hashes и source fingerprint. SQLite не изменилась. Предпросмотр не создавал staging и CF.

Лёгкая копия прошла 64 workspace-теста (61 прежний + 3 новых), включая полную прежнюю differential matrix пакетов. Новые тесты проверяют short-circuit A/B, защищённые свойства и порядок/перезапись вложенных членов. Strict Clippy и форматирование прошли. Это проверка прототипа; для переноса рекомендуется добавить отдельный интеграционный сценарий изменения StubSpec/present после первого output, наблюдающий именно Session hit/invalidation.

Независимый read-only агент `one_c_algorithm_review` выполнил два раздела — эффективность и обоснованность — по фактическому коду и сохранённым результатам. Подтверждённых дефектов лёгкого прототипа не найдено. Закреплённая роль — Sol 6.1 Ultra; отдельное runtime-свидетельство фактической модели не раскрыто. Ревьюер тесты не запускал.

## Границы и дальнейшее применение

Основные Rust-исходники, guards, GUI EXE и пользовательская конфигурация не изменены. GUI/native CF, приватные Git, UNC/ACL и массовые выборки существенно больше 92 заглушек в этом эксперименте не проверялись. Commit/push/публикация и сборка GUI EXE не выполнялись.

Рекомендация для следующего изменения — лёгкий Session memo, с интеграционными тестами инвалидации и повторением сравнений после переноса. Полный XML-кэш отклонён по фактическому расходу памяти. Дополнительный SQL-индекс не нужен: текущие lookup используют существующий primary key объектов и индекс регистраторов.
